# Ask Lizheng

How this repository, lizheng-personal-site (pages and storage gateway) and ask-lizheng-ops (owner dashboard and public questions) fit together around one Redis, who owns which keys and where each business rule is enforced: docs/ARCHITECTURE.md. Read it before changing anything another repository reads or writes.

User-facing name: 问问立正. A source-grounded AI interface over lizheng-open-context.

- Current product position (user reaffirmed 2026-10-04): public Q&A. Before submission, explain permission to save and publicly use the question, complete answer and sources. Sharing creates a link; it is not the initial public-use consent. Selected questions are published as asked (since 2026-10-05: the model only judges whether and names the topic), and every answered v4 question has its own page from the moment it is archived (2026-10-14). Situation text is not retained separately, but quoted details in an answer fall within disclosed public use. Preserve historical v1/v3 scopes. See docs/PRODUCT.md and docs/QUERY_RECORDS.md. In the app, name actual AI recipients before sending, and require fresh permission when the model, recipients, disclosure or archive/public mode changes. Since 2026-10-15 a backup (`BACKUP_MODELS`, OpenAI gpt-5) writes the answer when the model has written nothing in 30 seconds or failed before writing; the page notice, the app's consent and the privacy policy name it, and an app request uses it only when its consent named it (`ai_consent_backup`). Public-use consent does not establish a service provider's unverified protection or retention commitments.

- Use only the explicitly public Open Context projection for retrieval and answers. Never read private personal context, messages, community content or unpublished drafts. The authorized account integration may read only the signed-in user's verified identity and Circle Founding Member tag for access checks; never include these in model context.
- Open Context remains the content owner. data/context is a disposable, pinned copy with release hashes and license attribution.
- AI answers are AI synthesis/application, never Yuzheng replying live. Guest or community ideas retain their speakers; repository syntheses do not prove his stance. Answers name 立正 only for his own published writing or solo talks (`content_origin` yuzheng-published-text or yuzheng-spoken-source); when a sentence names him (any name in Open Context's `catalog/guest-names.json`) while citing other sources, the server asks for one rewrite. A guest is named only for a fragment whose speaker ID is that guest; people in a question are resolved through the same name table.
- Models select only retrieved source IDs. Server owns links, dates, timecodes and excerpts. Do not trust generated URLs or claim quotations without exact matching. Readers meet a source only as a citation mark: a source number written as a name ("S1 说得更直接", or in a heading, follow-up or reason) gets one rewrite request, as for naming 立正, and is then replaced by the source's title; the final answer numbers its sources 1 to n in reading order, while partial sections keep the model's numbers.
- At the user's explicit request, v1 disclosed question-only records remain unlinked and expire after their original 30 days. With ASK_OPS_ENABLED and the displayed v3 notice, new admitted questions are saved before generation; the complete validated public-facing answer and its selected source snapshots are saved before SSE result delivery. Retain v3 archives until the owner manually deletes them. v3 additionally saves pseudonymous browser/conversation IDs, server-assigned turn number, question character count, intent and entrypoint for private usage metrics; never describe browser IDs as verified people. Do not persist email, account identifier, IP, separately submitted background/history or raw model reasoning. An archived answer may quote background; disclose this. Under the v4 notice (2026-10-02, now the announced notice) the start record also carries notice_version v4, has_background ("1" whenever a situation or an earlier turn took part) and, until 2026-10-04, the situation text, kept for the owner only and never published. Since 2026-10-15 every question answered under the v4 notice is published as asked in the feed, the situation's included, and nothing judges whether others should see it (the owner: 「不要AI判断给不给别人看，全都放」); don't add such a gate. A conversation is one feed entry and one page, titled by its first answered question (the owner: 「多轮对话应该在同一个 URL 里边」): follow-ups are shown on that page, never as entries or pages of their own, and the page sends a reopened or reloaded conversation's follow-ups with its original conversation id. Ops' automatic feed asks /api/curate, signed with a key derived for that purpose alone and bound to its path, only for the topic of a question it publishes, and for the word of its page when it has none (v3); it never sees visitors, conversations or situations. The de-identifying v1 and the first batch's /api/themes and /api/seed-answer were retired on 2026-10-14/15, after Ops withdrew what they had published. An answered v4 result also carries `share` (record id, the model's topic word from its `slug`, and an HMAC proof under the quota-store key with prefix `ask-share:v1:`); only that page can ask lizheng.ai to give it a page at ask.lizheng.ai/s/<day>/<word>, which shows the question and answer, never the situation, and stops only when the record is deleted. The owner decided (2026-10-04): what can be shared goes to search engines, every shared page; sharing is a feature, not consent, so askers cannot withdraw a link; and the situation is no longer kept: since then the v4 start record carries has_background and an empty context, /api/meta says context_archive false, and the page says so where the situation is written. Missing-notice clients are excluded; v1 is never silently expanded or migrated. The conversation stays in memory; since 2026-10-05, at the user's request, each answered question (question, answer, sources and share proof; never the situation) is also kept on the device as 我的提问 (browser localStorage via `src/history.js`, one entry per conversation since 2026-10-15 with its conversation id and page, up to 50, deletable on the page, never sent anywhere), where the page explains that questions are kept with no identity, so this list is the only one; which questions this browser liked is remembered there too. Account scope remains daily3 public answers and verified Founding Member unlimited, with opaque quota metadata and encrypted short-lived authentication records. Sign-in may temporarily preserve the unsent draft in tab sessionStorage; clear on recovery. Analytics stays within the user-approved conversion scope (2026-10-02): Vercel Web Analytics page views and named click events, loaded only on lizheng.ai hosts; each event carries `surface` and at most one enumerated value, never question or situation text, source titles or identifiers. No other analytics. Inside the iPhone app (user agent `AskLizhengApp/`) the surface is `app`, membership purchase links and prices stay hidden (App Store guideline 3.1.1) while Founding verification stays, and the page tells the app through `window.webkit.messageHandlers.askApp` when pull-to-refresh would lose nothing. Before the app's first question the page asks once for permission to send it to the AI service (App Store guideline 5.1.2) and remembers the answer on the device; keep that step and its privacy policy link whenever data use changes.
- Model credentials are server-only; never put them in source, frontend, tests, screenshots or deployment env payloads.
- The service reads the corpus from the store the image builds (server/store.py, built by server/build_store.py in the Dockerfile; ASK_STORE=prebuilt there): never hold every passage in memory at start or per question. Every image must start in a 256 MB container with peak resident memory under 200 MB (scripts/check_image_memory.py, run by CI and before the context update commits). Values the store keeps are derived by the files in STORE_SOURCES (server/retrieval.py); changing one rebuilds the store. Retrieval must stay deterministic: the same question finds the same sources in every process.
- Builder's account (spend against its ceiling, the free hosting's end) is checked daily by .github/workflows/health.yml; lizheng.ai's daily check covers the rest (docs/ARCHITECTURE.md).
- The homepage only hands questions over (2026-10-15): its box opens this page with #q=<question> (src/home-question.js). Send such a question by itself only when the page was opened from www.lizheng.ai; from any other referrer, and for ?q=, only fill the box: a link must never ask for someone. Asking, answers, sharing, the count and sign-in exist only on this page.
- Public deploy, repository publication/push and upstream Open Context release require the exact reviewed payload and destination plus explicit user approval. One standing exception (user decision, 2026-10-04): pushing Open Context main approves its content, and `.github/workflows/update-context.yml` (scripts/update_context.py) brings each new release into data/, commits only data/ to main and deploys it with `config/builder-deploy.json`, stopping at the first failed check. Code and settings changes still need review and approval. Keep `config/builder-deploy.json` equal to the live settings; the update refuses to deploy when they differ. The deploy token also lives in this repository's `builder` environment: replace it there too when it changes.
- Open Context's parser runs only in credential-free child processes during updates (`scripts/update_context.py`); keep it that way. `tests/test_retrieval_eval.py` gates every update; refresh its stored query vectors with `scripts/retrieval_eval.py --refresh-vectors` when questions or the embedding model change.
- Test source attribution, response validation, input bounds, unsupported questions and upstream failures. Keep deployment compatible with Builder Space: root Dockerfile, PORT, one worker, 256 MB.
