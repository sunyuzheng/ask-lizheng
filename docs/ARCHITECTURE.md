# 问问立正的整体架构

2026-10-04 整理。三个仓库和一个数据库怎样配合、每份数据归谁、每条业务规则在哪执行，以及哪些地方会随用户增长变贵。改动跨仓库的功能前先读这一页；各仓库的细节仍在各自文档里，本页只写它们之间的关系。

## 四个部分

| 部分 | 仓库 | 跑在哪 | 负责 | 持有 |
|---|---|---|---|---|
| 主站 | lizheng-personal-site | Vercel，www.lizheng.ai 和 ask.lizheng.ai | 所有页面；浏览器能调用的所有接口；身份（访客 Cookie、Founding 登录）；替回答服务写数据 | 数据库读写凭证、登录与邮件凭证、各类签名密钥 |
| 回答服务 Builder | ask-lizheng（本仓库） | Builder Space（闲置5分钟会休眠） | 检索公开材料、调模型、校验回答；给后台整理公开问答 | 模型令牌；**没有**数据库凭证 |
| 后台 Ops | ask-lizheng-ops（私有） | Vercel | 立正的私人后台（问答记录、导出、删除、使用统计）；「别人在问什么」的公开数据（整理、发布、撤下、点赞） | 自己的数据库凭证 |
| 数据库 | — | 一个 Upstash Redis | 上面三者的全部状态 | 同一个库目前也给 Coffee Pass 用 |

ask.lizheng.ai 的页面文件由本仓库 `src/` 构建，再同步进主站 `client/public/ask-app/` 发布；Builder 只回答提问和 `/api/meta`。iPhone App 是这个页面的原生外壳（UA 带 `AskLizhengApp/`）。

## 每份数据归谁

写的一方是这份数据的主人，另一方只按约定读。键都是固定前缀，读写都走固定的 Lua 脚本，没有通用的数据库代理。

| 数据 | 键 | 写 | 读 |
|---|---|---|---|
| 每日次数账本 | `ask-quota:v1:*` | 主站（Builder 通过签名的 quota-storage 接口记账；分享多问一次由主站直接退回一次） | Builder（经主站）、主站 session |
| 访客网络计数 | `ask:net:v1:*` | 主站 | 主站 |
| 登录、会话、邮箱验证码 | `ask:auth:*` | 主站 | 主站 |
| v1 提问记录（30天） | `ask-query:v1:*` | 主站（Builder 通过签名的 query-storage 接口） | 立正本机脚本 |
| 问答存档（v3/v4） | `ask-ops:{v3}:record:*` 及其索引、计数 | 主站 writer（Builder 通过 query-storage 写开始和完成） | Ops（后台、整理）；主站（分享页） |
| 使用统计 | `ask-ops:{v3}:usage:*` | 主站（页面发来的匿名计数，加上分享接口自己记的） | Ops 后台 |
| 分享链接 | `ask-ops:{v3}:share:*`、`shares` | 主站 | 主站 |
| 公开问答 | `ask-ops:{v3}:discovery:*` | Ops | Ops；主站只经 Ops 的公开接口读，不直接读这些键 |

跨仓库的形状靠测试守着：Ops 用主站 writer 脚本的副本测存档记录（`tests/fixtures/writer-contract.json`）和使用统计（`tests/fixtures/usage-writer.json`）；分享证明的格式两边各有测试。

## 主要流程

1. **提问**：页面 → 主站 `/api/ask-lizheng/ask`：核验身份、按网络计访客次数、签名带上匿名访客和入口 → Builder `/api/ask`：经主站记账（每天3次，Founding 不限）、写开始记录 → 检索、生成、校验 → 写完成记录 → SSE 把回答传回页面。v4 已回答的结果附分享证明。
2. **自动整理和发布**：Ops 每15分钟（Vercel Cron）读新存档里可以公开的提问 → Builder `/api/curate`（签名）去掉个人信息、判断值不值得看、归到主题 → Ops 用检查过的脚本保存并发布，同时更新「最常问」的排序。
3. **别人在问什么**：页面 → 主站 `/api/ask-lizheng/discovery/lists`（CDN 缓存1分钟）→ Ops `lists`：最近问和最常问两份列表，每份30条，每个人看到的都一样。列表有变化（发布、撤下、修改、删除、点赞）时重算一次，读几十条数据；没变化时读者只花一次很小的读取或什么都不花。点开一条读 `detail`（同样缓存）；点赞经主站核验登录后签名交给 Ops。
4. **公开问答页** `www.lizheng.ai/ask/*`：主站读 Ops 的 `index`（全部公开问题一次读出）和 `detail`，渲染成可收录的页面，CDN 缓存10分钟。
5. **分享**：分享自己的回答 → 主站验证 Builder 的证明，给出 `ask.lizheng.ai/s/<日期>/<词>`，页面每次实时读存档记录；分享别人的问答 → 直接分享它的公开页 `www.lizheng.ai/ask/<id>`，不写数据库。
6. **使用统计**：页面打开时和离开时各发一次 → 主站固定脚本计数 → Ops 后台「使用情况」读。
7. **删除**：立正在 Ops 删一条存档 → 同一个脚本里删掉它的公开版本、点赞，更新排序；它的分享页随即 404。

## 业务规则在哪执行

| 规则 | 执行的地方 |
|---|---|
| 每天3次，Founding Member 不限 | Builder 判断，账本在主站 |
| 分享自己的回答，当天多问一次（每天一次；当天用过次数才给；Founding、微信、App 里不给） | 主站分享接口；页面只在可给时显示这句话 |
| v1、v3 永不公开；只有 v4、没带处境、首轮、不是「结合我的处境」、已回答的提问能公开 | Ops 保存和发布脚本（原子检查）；Ops 整理只挑这些；Builder `/api/curate` 去个人信息 |
| 「结合我的处境」不保存 | Builder 写记录时置空；页面在输入处写明 |
| 能分享的就给搜索引擎 | 分享页和公开问答页都可收录；公开问答页同一问法只收第一条、回答要有出处且够长 |
| 撤下、删除后消失 | 数据库里即时；列表和回答约2分钟内从缓存消失；公开问答页约10分钟；分享页即时 |
| 统计只记次数，不记内容 | 主站统计接口只收固定的标记 |
| 首页不显示播放量 | 主站页面 |

## 用户和问题变多时

- **每次打开页面的成本固定**。2026-10-04 之前，每来一个人，「别人在问什么」都要把全部公开问题重排两遍，每条问题读4次；免费的每月50万次读取四天用完，问题越多、人越多涨得越快。现在每个人看到同样的两份列表，读者由缓存直接给；列表只在变化时重算一次，只读列表里那几十条，和公开问题总数无关。最常问需要的「哪个主题被问得最多」在发布和撤下时就更新好了（Ops `shared/discovery-rank.ts`）。
- **容量**：公开问答最多存5000条（原来1000条，照每天三四十条约三周就满）。每条约20KB。
- **空间**：数据库套餐250MB（2026-10-04 起固定档，读取次数不限）。当天约7MB，每天涨1MB多一点，主要是问答存档；按这个速度能用半年左右，用户多了会更快。
- **流量**：公开问答页每次列表变化后读一遍全部公开问题。到两千条左右时，`/ask` 要改成分页，这一读也要分批。

## 出问题时

- 数据库是唯一的单点，所有功能都在上面，包括 Coffee Pass。2026-10-04 免费额度用完，问问立正全线停了约20分钟。现在套餐不限读取次数，出错时主站和 Ops 的日志会写原因（不含数据和密钥），可以直接从日志看出。
- Ops 停了：「别人在问什么」先由缓存撑一两分钟，之后换回示例问题；公开问答页的缓存撑得更久；提问照常。
- Builder 停了或在唤醒：不能提问，页面会说明；其他功能照常。
- 主站停了：全部停，回答服务和后台都要经过它。

## 维护

- 一个功能改到两三个仓库时，部署顺序是：后台（Ops）先上新接口，主站再上用它的页面（ask 页面随主站同步上线），回答服务只在回答相关的改动时部署。各仓库的部署步骤见各自的 AGENTS.md 和文档。
- 还有的重复，改的时候要两边一起改：主页问答区（TypeScript）和 ask.lizheng.ai 页面（JavaScript）各有一份「别人在问什么」的列表和卡片代码（规则由主站的测试守着）；存档回答的校验在主站和 Ops 各一份；使用统计的标记清单在主站和 Ops 各一份（主页的标记类型已直接用主站服务器那份）。
- 以后值得做的：把 Coffee Pass 挪到自己的数据库（免费档就够），两边互不影响；公开问题过两千条时把 `/ask` 分页；空间到七成时再决定升级套餐还是把旧存档移到更便宜的存储。
