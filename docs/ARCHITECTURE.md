# 问问立正的整体架构

2026-10-15更新（当天的架构体检之后）。公开资料仓库、产品仓库、一个数据库和两个文件存储怎样配合、每份数据归谁、每条业务规则在哪执行，哪些地方会随用户增长变贵，以及出了问题谁会知道。改动跨仓库的功能前先读这一页；各仓库的细节仍在各自文档里，本页只写它们之间的关系。这一页写的是现在的样子；各仓库按日期记的决定和经过在 PRODUCT.md、CHANGELOG.md 和各自的文档里。

## 各部分职责

| 部分 | 仓库 | 跑在哪 | 负责 | 持有 |
|---|---|---|---|---|
| 公开资料 | lizheng-open-context | GitHub | 原文、提炼、嘉宾与节目目录；版本化release | 公开来源、结构化关系、许可与manifest |
| 主站 | lizheng-personal-site | Vercel，www.lizheng.ai 和 ask.lizheng.ai | 所有页面；浏览器能调用的所有接口；身份（访客 Cookie、Founding 登录）；替回答服务写数据 | 数据库读写凭证、登录与邮件凭证、各类签名密钥 |
| 回答服务 Builder | ask-lizheng（本仓库） | Builder Space（256MB 的小容器，闲置会休眠） | 检索公开材料、调模型、校验回答；给后台公开的问题归主题 | 模型令牌；**没有**数据库凭证 |
| 后台 Ops | ask-lizheng-ops（私有） | Vercel | 立正的私人后台（问答记录、导出、删除、使用统计）；「别人在问什么」的公开数据（整理、发布、撤下、点赞） | 自己的数据库凭证 |
| 数据库 | — | 一个 Upstash Redis（Vercel 里叫 ask-lizheng-kv） | 上面三者的全部状态 | 只给问问立正用（Coffee Pass 2026-10-04 起用自己的库） |
| 文件存储 | — | 两个私有 Vercel Blob 存储，各用自己的令牌 | 给人看的东西写成的文件：公开问答（Ops 写、主站读）和分享过的回答的副本（主站写、Ops 删），令牌 `ASK_FILES_BLOB_TOKEN`；每天的备份（只有 Ops），令牌 `ASK_BACKUP_BLOB_TOKEN` | 2026-10-04 起：数据库出事时，看的人照常能看，数据也有30天的备份 |

ask.lizheng.ai 的页面文件由本仓库 `src/` 构建，再同步进主站 `client/public/ask-app/` 发布（`pnpm sync:ask-app`，只认本仓库最新的 main）；Builder 只回答提问、`/api/meta` 和材料地图的布局 `/api/answer-map`。iPhone、安卓 App 是这个页面的原生外壳（UA 带 `AskLizhengApp/`），微信小程序同理（UA 带 `miniProgram`）。

Builder 不把资料放在内存里（2026-10-15起）：构建镜像时 `server/build_store.py` 把固定版本的资料建成一个本地数据库文件 `data/store/ask.sqlite`（`server/store.py`：每段正文，和「每个汉字、每两个相邻汉字、每个英文词出现在哪些段落、几次、在不在标题里」的索引），回答时按问题的词查索引找候选，只把最后用到的十几段读出来。加载完约120MB（原来全部资料放内存，约260MB，平台上限256MB），资料翻一倍内存只多二三十兆（主要是语义向量）。

数据库在 Vercel Storage 里显示「没有连接项目」，因为主站和 Ops 的连接都是手工配的；它一直在用，别删。

2026-10-04明确的公开问答约定：用户在提问前同意保存和公开使用问题、完整回答与出处；取得分享链接是传播功能。自动精选与主动分享各有下面的展示规则，不能把自动精选的过滤条件理解为所有问答的公开使用边界。App发送前还单独说明Builder转发至DeepSeek生成回答、OpenAI匹配资料，并取得明确同意；邮箱与登录身份不交给AI。见[PRODUCT.md](PRODUCT.md)和[QUERY_RECORDS.md](QUERY_RECORDS.md)。

## 每份数据归谁

写的一方是这份数据的主人，另一方只按约定读。键都是固定前缀，读写都走固定的 Lua 脚本，没有通用的数据库代理。

| 数据 | 键 | 写 | 读 |
|---|---|---|---|
| 每日次数账本 | `ask-quota:v1:*` | 主站（Builder 通过签名的 quota-storage 接口记账；分享多问一次由主站直接退回一次） | Builder（经主站）、主站 session |
| 访客网络计数 | `ask:net:v1:*` | 主站 | 主站 |
| 反馈问题的计数（两天后删除） | `ask:report:v1:*` | 主站 | 主站 |
| 登录、会话、邮箱验证码 | `ask:auth:*` | 主站 | 主站 |
| v1 提问记录（30天） | `ask-query:v1:*` | 主站（Builder 通过签名的 query-storage 接口） | 立正本机脚本 |
| 问答存档（v3/v4） | `ask-ops:{v3}:record:*` 及其索引、计数 | 主站 writer（Builder 通过 query-storage 写开始和完成） | Ops（后台、整理）；主站（分享页） |
| 使用统计 | `ask-ops:{v3}:usage:*` | 主站（页面发来的匿名计数，加上分享接口自己记的） | Ops 后台 |
| 每个回答的网页（分享链接） | `ask-ops:{v3}:share:*`、`shares`，记录上的 `share_slug`、`shared_at` | 主站（回答存档时建；「结合我的处境」的由提问人分享时建）；2026-10-14 Ops 一次性给已公开、还没网页的问答补建过 | 主站；Ops 读记录上的网址写进公开问答 |
| 公开问答 | `ask-ops:{v3}:discovery:*` | Ops | Ops；主站只经 Ops 的公开接口或下面的文件读，不直接读这些键（每日体检读下面那一个除外） |
| 自动整理每轮的结果（何时跑完、游标到哪、为什么停） | `ask-ops:{v3}:discovery:curate-health` | Ops（每轮结束写一次） | 主站每日体检 |
| 最近一次每日备份（何时、多少个键、多大） | `ask-ops:{v3}:backup-health` | Ops（每次备份后） | 主站每日体检 |
| 每日体检的记录 | `ask:watch:v1:health`、`ask:watch:v1:db` | 主站 | 主站 |
| 公开问答的文件 | 文件存储 `public/`（lists、index、每条 detail、心跳 state） | Ops（导出过什么记在 `discovery:files:<存储>:*`） | 主站 |
| 分享过的回答的副本 | 文件存储 `share/<日期>/<词>.json` | 主站（分享时）；Ops 删（删记录之前） | 主站（数据库答不上来时） |
| 每天的备份 | 备份存储 `backup/<日期>.jsonl.gz`，留30天 | Ops | 立正恢复时 |

跨仓库的形状靠测试守着：Ops 用主站 writer 脚本的副本测存档记录（`tests/fixtures/writer-contract.json`）和使用统计（`tests/fixtures/usage-writer.json`）；分享证明的格式两边各有测试。存档回答里多了读取方还不认识的字段时，主站存档和各个读取方都只是不用它（`archivedAnswer` 的宽容读法，2026-10-15起），不会再像 10-11 那样整条读不出、让「别人在问什么」停更；格式坏了的已知字段照旧拒收，后台自己写的公开版本和立正在后台提交的内容也照旧严格。

**保存多久**：问答存档没有过期时间，不管公开没公开，问题、提问时间、回答和状态都一直留着，直到立正在后台删掉；后台可以把它们导出成含完整回答的文件。公开版本和整理时的判断也不过期。v1 提问记录按当时页面上说的30天到期自动删除（立正本机留了一份备份，不延长、不迁移）；「结合我的处境」从不保存。

## 主要流程

回答服务按用途选材：「想明白／结合处境」先限定立正的直接来源，再做关键词、语义与判断卡召回；问题问的是某位嘉宾的看法、没有问立正时，这位嘉宾本人被确认为陈述的片段也可作为他的观点来源，回答写明是他说的；「从哪读起」检索全库，包含独立的对谈索引。人物关联从Open Context的稳定ID读取，具体发言归属从原文片段读取。按嘉宾找资料直接返回相关节目与原文片段；普通问答涉及具名节目而没有立正的直接片段时，提供节目入口。页面分别列出本人材料与对谈资料，并由实际可用来源计算数量。

1. **提问**：ask.lizheng.ai 页面（主页的提问框只把问题交给它，2026-10-15 起）→ 主站 `/api/ask`（Edge 函数 `api/ask-lizheng.ts`）：核验身份、按网络计访客次数、签名带上匿名访客和入口 → Builder `/api/ask`。Vercel 要求 Edge 函数25秒内开始回话，而 Builder 的回应偶尔二十多秒才到主站（2026-10-15 两次，Builder 一两秒内就开始处理了）：所以主站12秒内没收到回应，就先给页面回话、边等边发心跳，之后 Builder 的回答照常流过来；Builder 晚到的拒绝（次数用完、模型变了、保存没确认）在流里变成同样字段的 error 事件，页面照原来的说法提示 →经主站记账（每天3次，Founding 不限）、写开始记录 → 检索、生成、校验 → 写完成记录（v4 已回答的带网址的词，主站存档时就建好这条回答的网页，「结合我的处境」的除外，回复里告诉 Builder）→ SSE 把回答连同网址传回页面。v4 已回答的结果另附分享证明。
2. **自动整理和发布**：Ops 每5分钟（Vercel Cron）读5分钟以前问的新存档，每个回答过的 v4 提问都发布，带处境的、接着问的、长的也一样，不判断值不值得看（2026-10-15 起，立正：「不要AI判断给不给别人看，全都放」）→ Builder `/api/curate`（签名，v3）只归主题，问题还没有自己的网页时另给网页地址的词，Ops 按主站的规则给它建网页（只看 2026-10-05 00:20 UTC 起问的，问题和回答原样公开；之前去掉个人信息改写的和第一批种子题 2026-10-14 撤下了）（Ops 从全部主题里挑出和这个问题最接近的，连同最常被问的，一共最多300个给它选）→ Ops 用检查过的脚本保存并发布（卡片带这条回答网页的网址 `share_url`），同时更新「最常问」的排序。
3. **别人在问什么**：页面 → 主站 `/api/ask-lizheng/discovery/lists`（CDN 缓存1分钟）→ 文件存储里 Ops 写好的 `public/lists.json`：最近问和最常问两份列表，每份30条，每个人看到的都一样。点开一条读 `detail`（同样缓存）。点赞不用登录（2026-10-05）：主站把浏览器的匿名访客标识换算成点赞专用的标识、按网络限量，再签名交给 Ops。最常问每个主题由点赞最多的那条代表，同主题的其他问题附在它下面（`similar`）。
   - **写文件（2026-10-04）**：公开问答一有变化（发布、撤下、修改、删除、点赞），Ops 就把列表、索引和变了的回答写成文件，写完一整套再写心跳 `public/state.json`。立正在后台操作后马上写一次，另外每分钟检查一次（Vercel Cron），把自动发布和点赞补上。撤下和删除的回答先删文件，再写列表。
   - **读文件**：主站只在心跳三分钟内的时候信文件，文件里没有的问题就当已撤下；心跳过期就问 Ops（列表有变化时重算一次，读几十条数据）；Ops 也答不上来，才拿最后一份文件顶上。所以写文件一直失败，也不会让撤下的问答留在网上，最慢和没有文件时一样。
4. **公开问答页** `www.lizheng.ai/ask/<日期>/<词>`：主站读 `index`（全部公开问题）和 `detail`，来源和第3条一样（先文件，后 Ops），渲染成可收录的页面，CDN 缓存10分钟。2026-10-14 起（立正：ask.lizheng.ai 也是 lizheng.ai 的一部分，「既能用 ask.lizheng.ai/url 也能给主站提供 SEO」）地址和这条问答在问问立正里的网页相同：人分享、打开、接着问用 `ask.lizheng.ai/s/<日期>/<词>`，它的 canonical 指向主站这一页，搜索引擎只读主站这一页；旧的 `/ask/<编号>` 301 跳过来。没进「别人在问什么」的回答没有主站页，网页仍在 ask 上。
5. **每个回答的网页和分享**（2026-10-14）：回答存档时主站就建好它的网页 `ask.lizheng.ai/s/<日期>/<词>`，回复 Builder 之后把这条回答的副本写进文件存储；「结合我的处境」的回答由提问人点了才建（主站验证 Builder 的证明）。网页每次实时读存档记录（删除立刻生效，真人打开要计数），只在数据库答不上来时用副本，数据库说没有了就不用副本。复制、发送或打开二维码才算分享，主站记一次。「别人在问什么」的每一条分享的就是它自己的网页；之前给出去的 `ask.lizheng.ai/q/<id>` 跳过去。
6. **使用统计**：页面打开时和离开时各发一次 → 主站固定脚本计数 → Ops 后台「使用情况」读。
7. **删除**：立正在 Ops 删一条存档 → 先删它分享页的副本（删不掉就不删记录，让立正稍后再试）→ 同一个脚本里删掉记录、它的公开版本、点赞，更新排序 → 马上重写公开文件，删掉它那一条。它的分享页随即 404。
8. **资料更新**：Open Context同时拥有原文、提炼和嘉宾结构化数据。网站嘉宾页从固定commit及manifest生成；本服务的语料和索引从同一release生成。Open Context推到main → 本仓库 GitHub 上的 `update-context` 半小时内发现，校验、同步、重建索引（只算改过的文字）和材料地图、测试，把 `data/` 提交到 main，部署 Builder，等线上答到新版本为止（README「公开资料」）。
9. **每天的备份**：Ops 每天 03:17 UTC 把 `ask-ops:{v3}:` 下所有的键写成一份，放进只有 Ops 能读的备份存储，留30天（Ops 仓库 docs/backup.md，有恢复脚本）。v1 记录不备份（承诺30天，不延长）。
10. **反馈问题**（2026-10-15）：页面（等回答时、回答没完成后、回答下面、首屏底部）→ 主站 `/api/ask-lizheng/report`：检查固定格式（本仓库 `src/report.js` 发，同步到主站 `shared/ask-report-client.js`，主站的测试拿它核对接口）、按网络和全站限量 → 用登录验证码那把 Resend key 发邮件给立正。不进存档、不经 Builder 和 Ops；处境从不在里面。见 [PRODUCT.md](PRODUCT.md)「反馈问题」。

11. **每日体检**（2026-10-15）：主站的定时任务每天 04:00 UTC（Ops 备份之后）只读次数和时间，有问题才给立正发一封信（`shared/ask-health.ts`）：昨天的提问大多没答完或有几个一直没结果；自动整理两小时没跑完、停在某条记录或数据库上、落后最新提问三小时以上；公开文件的心跳超过15分钟；最近一次备份超过30小时；公开问答到了容量的八成（每周最多提一次）；回答服务没有正常回应。需要 Builder 令牌的几项（AI 花费离上限还有多少、免费托管哪天到期、部署状态、线上是不是 Open Context 最新一版）由本仓库的 `health` 工作流每天查（`scripts/builder_health.py`），出问题这次运行失败、GitHub 发信。

## 业务规则在哪执行

| 规则 | 执行的地方 |
|---|---|
| 每天3次，Founding Member 不限 | Builder 判断，账本在主站 |
| 分享自己的回答，当天多问一次（每天一次；当天用过次数才给；Founding、微信、App 里不给） | 主站分享接口；页面只在可给时显示这句话 |
| v1、v3 永不公开；每个 2026-10-05 00:20 UTC 起问的 v4 已回答问答都原样公开（2026-10-15 起，带处境和接着问的也一样，不由 AI 判断）；每个 v4 已回答的问答存档时就有网页（2026-10-15 起含处境的回答也一样） | Ops 保存和发布脚本检查 v4、完整回答、提问时间和网页；主站存档脚本建网页、分享接口检查 v4 与完整回答 |
| 「结合我的处境」原文不保存；回答可能引用其中细节，并在提问前披露的范围内公开使用 | Builder 写记录时置空原文；页面在输入处和同意说明里写明 |
| 能分享的就给搜索引擎 | 公开问答在主站 `www.lizheng.ai/ask/<日期>/<词>` 收录（ask 上同地址的网页把 canonical 指过去）；没公开的回答在 ask 上收录；公开问答页同一问法只收第一条、回答要有出处且够长 |
| 撤下、删除后消失（撤下只从「别人在问什么」和公开问答页拿掉，回答自己的网页还在；删记录网页才没） | 数据库里即时；文件在立正操作后马上重写（最晚下一分钟）；列表和回答约2分钟内从缓存消失；公开问答页约10分钟；分享页即时（副本在删记录之前就删了）；之前的备份里最多再留30天 |
| 统计只记次数，不记内容 | 主站统计接口只收固定的标记 |
| 反馈问题：同一网络每天10条、全站每天40封；我们自己的无头浏览器和爬虫不发邮件；不带处境 | 主站 `shared/ask-report.ts`；页面 `src/report.js` 只发固定字段 |
| 首页不显示播放量 | 主站页面 |
| 点赞不用登录，按浏览器计数；同一网络每天给同一条最多20次、总共500次 | 主站点赞接口（`resolveDiscoveryVoter`）；Ops 每个点赞标识每分钟最多60次改动 |
| 「我的提问」只存在本机，不发给任何服务；不存处境原文 | ask 页面的 `src/history.js`（浏览器存储，最多50条） |

## 用户和问题变多时

- **回答服务的内存和速度**（2026-10-15）。资料存在镜像里的本地索引文件里，服务启动约0.2秒读完索引、内存约120MB；找一次材料0.01–0.1秒（原来逐段扫描两千多万字，0.3–0.6秒，平台的机器还要慢几倍）。内存随资料增长的主要是语义向量（每段约1KB）。同时最多答3个问题（`ASK_CONCURRENCY`）的限制没变。
- **看的人不碰数据库**（2026-10-04）。「别人在问什么」和公开问答页读的是文件；数据库只在有人提问、点赞、分享和写文件时用到。
- **每次打开页面的成本固定**。2026-10-04 之前，每来一个人，「别人在问什么」都要把全部公开问题重排两遍，每条问题读4次；免费的每月50万次读取四天用完，问题越多、人越多涨得越快。现在每个人看到同样的两份列表，读者由缓存直接给；列表只在变化时重算一次，只读列表里那几十条，和公开问题总数无关。最常问需要的「哪个主题被问得最多」在发布和撤下时就更新好了（Ops `shared/discovery-rank.ts`）。
- **容量**：公开问答最多存5000条（原来1000条，照每天三四十条约三周就满）。每条约20KB。
- **空间**：数据库套餐250MB（2026-10-04 起固定档，读取次数不限）。当天约7MB，每天涨1MB多一点，主要是问答存档；按这个速度能用半年左右，用户多了会更快。库的 Settings 里开了 Auto Upgrade，快满时 Upstash 自动升到大一档；主站每天 01:00 UTC 查一次套餐大小，变了就给立正发邮件（`api/ask-lizheng-db-watch.ts`）。
- **流量**：公开问答页每次列表变化后读一遍全部公开问题。到两千条左右时，`/ask` 要改成分页，这一读也要分批。

## 出问题时

出了问题谁会知道：每日体检（上面第11条）和 Builder 的 `health` 工作流；资料自动更新失败、Open Context 通知失败，GitHub 发信；数据库换套餐、会员核验快到上限，主站发信；用户在页面上点「反馈问题」，直接发到立正的邮箱。

- 数据库停了：不能提问、点赞、生成分享链接；「别人在问什么」、公开问答页和分享页照常（读文件和副本）。2026-10-04 免费额度用完时，问问立正全线停了约20分钟，那时还没有文件。现在套餐不限读取次数，出错时主站和 Ops 的日志会写原因（不含数据和密钥）。
- 数据坏了或丢了：Ops 每天的备份留30天（`scripts/restore-backup.ts`，先恢复到新库比对）；Upstash 自己也每天做一份（只留最近一份，在控制台 Backups 里恢复）；Ops 后台还能导出全部问答。
- Ops 停了：「别人在问什么」和公开问答页照常读文件（心跳过期后先问 Ops，问不到就用最后一份文件）；新发布的问答等 Ops 恢复后才出现；提问照常。
- 文件存储停了：主站读不到文件就问 Ops，和没有文件之前一样；分享页没有副本可用；每天的备份那天缺一份。
- Builder 停了或在唤醒：不能提问，页面会说明；其他功能照常。
- 主站停了：全部停，回答服务和后台都要经过它。

## 维护

- 一个功能改到两三个仓库时，部署顺序是：后台（Ops）先上新接口，主站再上用它的页面（ask 页面随主站同步上线），回答服务只在回答相关的改动时部署。各仓库的部署步骤见各自的 AGENTS.md 和文档。
- 文件存储的令牌：`ASK_FILES_BLOB_TOKEN` 在主站和 Ops 各配一份（同一个存储），`ASK_BACKUP_BLOB_TOKEN` 只在 Ops。主站原有的 `BLOB_READ_WRITE_TOKEN` 是社区地图的公开存储，别混用。换存储时 Ops 会从头写一遍公开文件（导出记录按存储分开）。
- 只有一个提问页（2026-10-15 起）：主页问答区只是入口，提问框把问题交给 ask.lizheng.ai（`#q=`，`src/home-question.js`），「别人在问什么」的每一条打开它自己的网页；提问、回答、地图、分享栏、反馈只在本仓库的页面里。还有的重复，改的时候要两边一起改：「别人在问什么」的列表主页（TypeScript，`client/src/lib/ask-discovery.ts`）和这一页（`src/discovery.js`）各一份，规则由主站的测试守着；经 `pnpm sync:ask-app` 拷过去共用的有公开问答说明、反馈的格式、出处归属、页面骨架；存档回答的校验在主站和 Ops 各一份（保持一字不差）；使用统计的标记清单在主站和 Ops 各一份（主页的标记类型已直接用主站服务器那份）。
- 资料推到 Open Context main 就自动上线，不用手动同步；出错时 GitHub 发邮件给立正，修好后下一轮自动补上。Builder 的部署设置以 `config/builder-deploy.json` 为准：改线上设置要同时改它，否则自动更新不部署。部署令牌在 GitHub 的 `builder` 环境里也有一份，换令牌要一起换。
- **上线前的内存关**：Builder 的镜像在 CI 和资料自动更新里都会在256MB的容器里试启动一遍（`scripts/check_image_memory.py`），服务进程最高内存超过200MB就不上线；资料自动更新因此失败时，GitHub 发信。
- **一个问题的词**：问题拆出的词超过保留的数量（自己的70个）时，同样长短的词按在问题里出现的先后取（2026-10-15起；之前随服务器每次启动的随机设置变化，长问题在不同时间问可能找到不同材料）。
- 以后值得做的：公开问题过两千条时把 `/ask` 分页；收到升级邮件时，看看是继续用大一档，还是把旧存档移到更便宜的存储；Builder 的免费托管到 2027-10-01（平台写的是首次部署起一年），到期前要找讲师延期或换地方（`health` 工作流提前60天报警）；v1 提问记录 2026-10-31 前后全部到期，之后可以删掉 v1 那条存档路径。
