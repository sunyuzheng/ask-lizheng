# 问问立正的整体架构

2026-10-04 整理。三个仓库、一个数据库和两个文件存储怎样配合、每份数据归谁、每条业务规则在哪执行，以及哪些地方会随用户增长变贵。改动跨仓库的功能前先读这一页；各仓库的细节仍在各自文档里，本页只写它们之间的关系。

## 五个部分

| 部分 | 仓库 | 跑在哪 | 负责 | 持有 |
|---|---|---|---|---|
| 主站 | lizheng-personal-site | Vercel，www.lizheng.ai 和 ask.lizheng.ai | 所有页面；浏览器能调用的所有接口；身份（访客 Cookie、Founding 登录）；替回答服务写数据 | 数据库读写凭证、登录与邮件凭证、各类签名密钥 |
| 回答服务 Builder | ask-lizheng（本仓库） | Builder Space（闲置5分钟会休眠） | 检索公开材料、调模型、校验回答；给后台整理公开问答 | 模型令牌；**没有**数据库凭证 |
| 后台 Ops | ask-lizheng-ops（私有） | Vercel | 立正的私人后台（问答记录、导出、删除、使用统计）；「别人在问什么」的公开数据（整理、发布、撤下、点赞） | 自己的数据库凭证 |
| 数据库 | — | 一个 Upstash Redis（Vercel 里叫 ask-lizheng-kv） | 上面三者的全部状态 | 只给问问立正用（Coffee Pass 2026-10-04 起用自己的库） |
| 文件存储 | — | 两个私有 Vercel Blob 存储，各用自己的令牌 | 给人看的东西写成的文件：公开问答（Ops 写、主站读）和分享过的回答的副本（主站写、Ops 删），令牌 `ASK_FILES_BLOB_TOKEN`；每天的备份（只有 Ops），令牌 `ASK_BACKUP_BLOB_TOKEN` | 2026-10-04 起：数据库出事时，看的人照常能看，数据也有30天的备份 |

ask.lizheng.ai 的页面文件由本仓库 `src/` 构建，再同步进主站 `client/public/ask-app/` 发布；Builder 只回答提问和 `/api/meta`。iPhone App 是这个页面的原生外壳（UA 带 `AskLizhengApp/`）。

数据库在 Vercel Storage 里显示「没有连接项目」，因为主站和 Ops 的连接都是手工配的；它一直在用，别删。

2026-10-04明确的公开问答约定：用户在提问前同意保存和公开使用问题、完整回答与出处；取得分享链接是传播功能。自动精选与主动分享各有下面的展示规则，不能把自动精选的过滤条件理解为所有问答的公开使用边界。App发送前还单独说明Builder转发至DeepSeek生成回答、OpenAI匹配资料，并取得明确同意；邮箱与登录身份不交给AI。见[PRODUCT.md](PRODUCT.md)和[QUERY_RECORDS.md](QUERY_RECORDS.md)。

## 每份数据归谁

写的一方是这份数据的主人，另一方只按约定读。键都是固定前缀，读写都走固定的 Lua 脚本，没有通用的数据库代理。

| 数据 | 键 | 写 | 读 |
|---|---|---|---|
| 每日次数账本 | `ask-quota:v1:*` | 主站（Builder 通过签名的 quota-storage 接口记账；分享多问一次由主站直接退回一次） | Builder（经主站）、主站 session |
| 访客网络计数 | `ask:net:v1:*` | 主站 | 主站 |
| 登录、会话、邮箱验证码 | `ask:auth:*` | 主站 | 主站 |
| v1 提问记录（30天） | `ask-query:v1:*` | 主站（Builder 通过签名的 query-storage 接口） | 立正本机脚本 |
| 问答存档（v3/v4） | `ask-ops:{v3}:record:*` 及其索引、计数 | 主站 writer（Builder 通过 query-storage 写开始和完成） | Ops（后台、整理）；主站（分享页） |
| 使用统计 | `ask-ops:{v3}:usage:*` | 主站（页面发来的匿名计数，加上分享接口自己记的） | Ops 后台 |
| 分享链接 | `ask-ops:{v3}:share:*`、`shares` | 主站 | 主站 |
| 公开问答 | `ask-ops:{v3}:discovery:*` | Ops | Ops；主站只经 Ops 的公开接口或下面的文件读，不直接读这些键 |
| 公开问答的文件 | 文件存储 `public/`（lists、index、每条 detail、心跳 state） | Ops（导出过什么记在 `discovery:files:<存储>:*`） | 主站 |
| 分享过的回答的副本 | 文件存储 `share/<日期>/<词>.json` | 主站（分享时）；Ops 删（删记录之前） | 主站（数据库答不上来时） |
| 每天的备份 | 备份存储 `backup/<日期>.jsonl.gz`，留30天 | Ops | 立正恢复时 |

跨仓库的形状靠测试守着：Ops 用主站 writer 脚本的副本测存档记录（`tests/fixtures/writer-contract.json`）和使用统计（`tests/fixtures/usage-writer.json`）；分享证明的格式两边各有测试。

**保存多久**：问答存档没有过期时间，不管公开没公开，问题、提问时间、回答和状态都一直留着，直到立正在后台删掉；后台可以把它们导出成含完整回答的文件。公开版本和整理时的判断也不过期。v1 提问记录按当时页面上说的30天到期自动删除（立正本机留了一份备份，不延长、不迁移）；「结合我的处境」从不保存。

## 主要流程

1. **提问**：页面 → 主站 `/api/ask-lizheng/ask`：核验身份、按网络计访客次数、签名带上匿名访客和入口 → Builder `/api/ask`：经主站记账（每天3次，Founding 不限）、写开始记录 → 检索、生成、校验 → 写完成记录 → SSE 把回答传回页面。v4 已回答的结果附分享证明。
2. **自动整理和发布**：Ops 每15分钟（Vercel Cron）读新存档里可以公开的提问 → Builder `/api/curate`（签名）去掉个人信息、判断值不值得看、归到主题（Ops 从全部主题里挑出和这个问题最接近的，连同最常被问的，一共最多300个给它选）→ Ops 用检查过的脚本保存并发布，同时更新「最常问」的排序。
3. **别人在问什么**：页面 → 主站 `/api/ask-lizheng/discovery/lists`（CDN 缓存1分钟）→ 文件存储里 Ops 写好的 `public/lists.json`：最近问和最常问两份列表，每份30条，每个人看到的都一样。点开一条读 `detail`（同样缓存）；点赞经主站核验登录后签名交给 Ops。
   - **写文件（2026-10-04）**：公开问答一有变化（发布、撤下、修改、删除、点赞），Ops 就把列表、索引和变了的回答写成文件，写完一整套再写心跳 `public/state.json`。立正在后台操作后马上写一次，另外每分钟检查一次（Vercel Cron），把自动发布和点赞补上。撤下和删除的回答先删文件，再写列表。
   - **读文件**：主站只在心跳三分钟内的时候信文件，文件里没有的问题就当已撤下；心跳过期就问 Ops（列表有变化时重算一次，读几十条数据）；Ops 也答不上来，才拿最后一份文件顶上。所以写文件一直失败，也不会让撤下的问答留在网上，最慢和没有文件时一样。
4. **公开问答页** `www.lizheng.ai/ask/*`：主站读 `index`（全部公开问题）和 `detail`，来源和第3条一样（先文件，后 Ops），渲染成可收录的页面，CDN 缓存10分钟。
5. **分享**：分享自己的回答 → 主站验证 Builder 的证明，给出 `ask.lizheng.ai/s/<日期>/<词>`，同时把这条回答的副本写进文件存储；分享页每次实时读存档记录（删除立刻生效，真人打开要计数），只在数据库答不上来时用副本，数据库说没有了就不用副本。分享别人的问答 → 直接分享它的公开页 `www.lizheng.ai/ask/<id>`，不写数据库。
6. **使用统计**：页面打开时和离开时各发一次 → 主站固定脚本计数 → Ops 后台「使用情况」读。
7. **删除**：立正在 Ops 删一条存档 → 先删它分享页的副本（删不掉就不删记录，让立正稍后再试）→ 同一个脚本里删掉记录、它的公开版本、点赞，更新排序 → 马上重写公开文件，删掉它那一条。它的分享页随即 404。
8. **资料更新**：Open Context 推到 main → 本仓库 GitHub 上的 `update-context` 半小时内发现，校验、同步、重建索引（只算改过的文字）、测试，把 `data/` 提交到 main，部署 Builder，等线上答到新版本为止（README「公开资料」）。
9. **每天的备份**：Ops 每天 03:17 UTC 把 `ask-ops:{v3}:` 下所有的键写成一份，放进只有 Ops 能读的备份存储，留30天（Ops 仓库 docs/backup.md，有恢复脚本）。v1 记录不备份（承诺30天，不延长）。

## 业务规则在哪执行

| 规则 | 执行的地方 |
|---|---|
| 每天3次，Founding Member 不限 | Builder 判断，账本在主站 |
| 分享自己的回答，当天多问一次（每天一次；当天用过次数才给；Founding、微信、App 里不给） | 主站分享接口；页面只在可给时显示这句话 |
| v1、v3 永不公开；自动精选只取符合条件的 v4 已回答问答（无处境/历史、非apply）；主动分享可展示已回答的 v4 问答及其出处，包括含处境细节的回答 | Ops 保存和发布脚本检查精选条件，Builder `/api/curate` 去个人信息；主站分享接口检查 v4 与完整回答 |
| 「结合我的处境」原文不保存；回答可能引用其中细节，并在提问前披露的范围内公开使用 | Builder 写记录时置空原文；页面在输入处和同意说明里写明 |
| 能分享的就给搜索引擎 | 分享页和公开问答页都可收录；公开问答页同一问法只收第一条、回答要有出处且够长 |
| 撤下、删除后消失 | 数据库里即时；文件在立正操作后马上重写（最晚下一分钟）；列表和回答约2分钟内从缓存消失；公开问答页约10分钟；分享页即时（副本在删记录之前就删了）；之前的备份里最多再留30天 |
| 统计只记次数，不记内容 | 主站统计接口只收固定的标记 |
| 首页不显示播放量 | 主站页面 |

## 用户和问题变多时

- **看的人不碰数据库**（2026-10-04）。「别人在问什么」和公开问答页读的是文件；数据库只在有人提问、点赞、分享和写文件时用到。
- **每次打开页面的成本固定**。2026-10-04 之前，每来一个人，「别人在问什么」都要把全部公开问题重排两遍，每条问题读4次；免费的每月50万次读取四天用完，问题越多、人越多涨得越快。现在每个人看到同样的两份列表，读者由缓存直接给；列表只在变化时重算一次，只读列表里那几十条，和公开问题总数无关。最常问需要的「哪个主题被问得最多」在发布和撤下时就更新好了（Ops `shared/discovery-rank.ts`）。
- **容量**：公开问答最多存5000条（原来1000条，照每天三四十条约三周就满）。每条约20KB。
- **空间**：数据库套餐250MB（2026-10-04 起固定档，读取次数不限）。当天约7MB，每天涨1MB多一点，主要是问答存档；按这个速度能用半年左右，用户多了会更快。库的 Settings 里开了 Auto Upgrade，快满时 Upstash 自动升到大一档；主站每天 01:00 UTC 查一次套餐大小，变了就给立正发邮件（`api/ask-lizheng-db-watch.ts`）。
- **流量**：公开问答页每次列表变化后读一遍全部公开问题。到两千条左右时，`/ask` 要改成分页，这一读也要分批。

## 出问题时

- 数据库停了：不能提问、点赞、生成分享链接；「别人在问什么」、公开问答页和分享页照常（读文件和副本）。2026-10-04 免费额度用完时，问问立正全线停了约20分钟，那时还没有文件。现在套餐不限读取次数，出错时主站和 Ops 的日志会写原因（不含数据和密钥）。
- 数据坏了或丢了：Ops 每天的备份留30天（`scripts/restore-backup.ts`，先恢复到新库比对）；Upstash 自己也每天做一份（只留最近一份，在控制台 Backups 里恢复）；Ops 后台还能导出全部问答。
- Ops 停了：「别人在问什么」和公开问答页照常读文件（心跳过期后先问 Ops，问不到就用最后一份文件）；新发布的问答等 Ops 恢复后才出现；提问照常。
- 文件存储停了：主站读不到文件就问 Ops，和没有文件之前一样；分享页没有副本可用；每天的备份那天缺一份。
- Builder 停了或在唤醒：不能提问，页面会说明；其他功能照常。
- 主站停了：全部停，回答服务和后台都要经过它。

## 维护

- 一个功能改到两三个仓库时，部署顺序是：后台（Ops）先上新接口，主站再上用它的页面（ask 页面随主站同步上线），回答服务只在回答相关的改动时部署。各仓库的部署步骤见各自的 AGENTS.md 和文档。
- 文件存储的令牌：`ASK_FILES_BLOB_TOKEN` 在主站和 Ops 各配一份（同一个存储），`ASK_BACKUP_BLOB_TOKEN` 只在 Ops。主站原有的 `BLOB_READ_WRITE_TOKEN` 是社区地图的公开存储，别混用。换存储时 Ops 会从头写一遍公开文件（导出记录按存储分开）。
- 还有的重复，改的时候要两边一起改：主页问答区（TypeScript）和 ask.lizheng.ai 页面（JavaScript）各有一份「别人在问什么」的列表和卡片代码（规则由主站的测试守着）；存档回答的校验在主站和 Ops 各一份；使用统计的标记清单在主站和 Ops 各一份（主页的标记类型已直接用主站服务器那份）。
- 资料推到 Open Context main 就自动上线，不用手动同步；出错时 GitHub 发邮件给立正，修好后下一轮自动补上。Builder 的部署设置以 `config/builder-deploy.json` 为准：改线上设置要同时改它，否则自动更新不部署。部署令牌在 GitHub 的 `builder` 环境里也有一份，换令牌要一起换。
- 以后值得做的：公开问题过两千条时把 `/ask` 分页；收到升级邮件时，看看是继续用大一档，还是把旧存档移到更便宜的存储；Builder 的免费托管到 2027-10-01（平台写的是首次部署起一年），到期前要找讲师延期或换地方。
